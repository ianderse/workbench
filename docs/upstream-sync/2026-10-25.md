## Decisions needed

Defaults below favour our behaviour, per the sync rules. Owner's choices are marked on each item.

1. **Owner's choice: Unified.** `mergeTargetIntoBranch` (`ai/runners/merge-target-into-branch.ts`) is now the one implementation of "bring the target into the task branch and resolve conflicts"; `autoMergeIntoTarget` calls it too (its own copy is gone), alongside PR merge, local merge and resync without a session. Autonomous keeps its temp-worktree `--no-ff` merge, `advanceBranch` and per-project serialization. Conflict help goes through `runMergeAgent` -> `runClaudeText`, so OMP works. Original note: **Merge conflicts of a PR merge / local merge.** Upstream: a local merge first pulls the base into the task branch and lets Claude Code resolve conflicts (`worktree/local-merge.ts`, `merge-target-into-branch.ts`), with many safety checks. Ours: the same agent is used by autonomous merge and PR merge. Chosen: upstream's code for PR/local merges (it does not overlap), ours for autonomous (its own temporary-worktree merge, now sharing upstream's check helpers). Alternative: route autonomous merges through upstream's `mergeTargetIntoBranch`. Recommend: later, once autonomous mode has settled; two implementations of one check is a maintenance cost.
2. **Owner's choice: Done: resync on auto-merge.** `autonomous-service` emits the `auto-merged` task hook after a successful auto-merge; `TaskNotices.onAutoMerged` runs the same merge sync as for Done, against the target the tasks branch from (integration branch, via the `autonomousTarget` option, or the task's base). Auto-merged tasks are never resynced, and an auto-merged task moving to Done does not trigger it again (`announcesMergeOnDone`, `takesInMerge`; a reverted auto-merge counts as not merged). Original note: **Resync after merges vs autonomous mode.** Upstream: when a task is merged (state `done`), other tasks on that base go back to In Progress and merge it in. Ours: autonomous mode already pulls the target into each task branch right before auto-merging it, and tasks start from the integration branch. Chosen: both stay; the resync trigger fires on `done`, not on `auto_merged`, so auto-merges into the integration branch do not resync siblings. Alternative: also trigger merge sync from `auto_merged` (adopt theirs fully). Recommend: wire it later and test, because it would restart sibling tasks mid-queue.
3. **Owner's choice: Kept.** **Validation skip rule.** Upstream: validate again when a resync or revise came after the last validation. Ours: AI review loop with rounds and verdict. Chosen: combine: the loop runs when the report is missing or any coding step is newer than the last validation. Alternative: ours only (a resynced task would keep an old verdict). Recommend: keep the combination.
4. **Owner's choice: Kept** (still to check against real ledger rows). **Usage ledger for multi-turn runs.** Upstream's keep-open runs can produce several results per process. Chosen: book each result. Alternative: book the last only (undercounts), or sum then book once. Recommend: check a real messaging run's ledger rows, since CLI totals may be cumulative per session.
5. **Owner's choice: Kept.** **Agent window system prompt.** Upstream merges Graphify and self-improve into one flag for Claude windows; ours had separate OMP flags. Chosen: both (Claude gets upstream's; OMP unchanged). Alternative: unify OMP too. Recommend: leave, OMP's memory prompt is longer and differs.
6. **Owner's choice: Kept (OMP gap).** **Task messaging settings placement.** Upstream shows the switch for everyone. Chosen: hidden under OMP (no effect there). Alternative: show it disabled with a note. Recommend: fine as is.
7. **Owner's choice: Done.** `backend` (from `resolveEffectiveAgent`) is passed through `mergeTargetIntoBranch` -> `MergeAgentInput` -> `runClaudeText` by resync without a session (`task-runner`), autonomous auto-merge, PR merge and local merge. Original note: **Per-task backend pin and merge helper.** `mergeTargetIntoBranch` (resync without a session) calls `runMergeAgent`, which uses the app-wide backend, not a task pinned to the other backend. Same limitation as our existing merge help. Recommend: pass `backend` through when a pin exists (small follow-up).

## OMP gaps (upstream features available on Claude Code only)

- **Task messaging** (`message_task`, `list_parallel_tasks`, inbox delivery into a live session): served by Workbench's local MCP server and `--replay-user-messages`; OMP gets no Workbench MCP tools. `config.messaging` is not set for OMP tasks, the Settings switch is hidden under OMP, and `startOmpProcess` has a no-op `send`. OMP tasks still get the changelog-based "Parallel tasks" prompt.
- **Live messages and notices to a running session**: the "task started / finished / edits the same files" notices are queued to inboxes; OMP tasks never read them.
- **Live agent graph fixes** (`live-agent/relay`): Claude Code transcripts and hooks only; OMP windows are not drawn there (unchanged).
- **Resync with a session**: works on OMP through the shared `runSessionPhase('resync')` (merge in the task's session, or the merge helper when there is no session), but the session-resume paths and the "continue the stopped implementation in the same turn" shortcut were only tested against Claude Code.
- **Usage badge fixes** (account switch, loading timeout): Claude accounts; the OMP edition still skips Claude usage polling entirely.
- **`--name` / native SendMessage**: Claude Code CLI only.
